# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`nachbarin` is a Cloudflare Worker (TypeScript) exposing a data-capture API for museum exhibits: exhibition software ("apps") POSTs records of visitor interactions, and an operator bulk-downloads them incrementally. Two endpoints, both under `/v1/records` — POST to write, GET to read. See `README.md` for the product context.

**Vocabulary.** An **app** is the software module (`future-mobility-simulator`); an **instance** is where it runs (a museum, or one copy of a travelling exhibition); an **installation** is the `(app, instance)` pair. A record belongs to an installation, and every API key grants exactly one — `read` and `write` are the two kinds, and both are installation-scoped. Use these three words precisely — "exhibit" means the physical thing in the museum (furniture, hardware, texts) and is never an identifier.

**Both storage seams are live, and there is no third one.** `src/storage.ts` defines `KeyStore`/`RecordStore`; both are implemented against D1 (`src/d1-key-store.ts`, `src/d1-record-store.ts`). The whole request path is complete — records are written, deduplicated, paged and read for real. The submission log (`0004`) is deliberately **not** a new seam, and earlier notes predicting one were wrong: its rows must be written in the record insert's transaction, so a seam between them would be a seam across a transaction boundary. It is a parameter on `RecordStore.insert` instead. `NotImplementedError` and the 501 it mapped to are gone — nothing was ever going to throw it.

**Records store dates, never times, and that is the design.** A record keeps `created_date` (the date of the client's `created_at`, exhibit-local) and `received_date` (server, UTC). The exact timestamps go to `record_submissions`, with its own access (none — it has no endpoint) and its own retention (90 days, by cron). `app_data` is coarse enough to be uninteresting alone; a precise timestamp is not, because against camera footage or a ticket scan it identifies who made which choice. Read the header of `migrations/0003_create_records.sql` before touching either column.

**The submission log is per-_submission_, not per-record.** `record_submissions` gets one row per submitted record per POST, **including duplicates** — the grain is the whole point, since a resubmission stores no record and would otherwise be invisible (a queue that stopped draining, a replayed batch, a resend with mutated `app_data`). Per-record metadata is a view over it: the earliest row per `(installation_pk, client_id)` is the creating submission. It has no FK to `records`, deliberately — read the header of `migrations/0004_log_record_submissions.sql` before adding one.

## Commands

- `npm run dev` (or `npm start`) — local dev server via `wrangler dev` (http://localhost:8787)
- `npm run deploy` — deploy to Cloudflare via `wrangler deploy`
- `npm test` — run the vitest suite in watch mode
- `npx vitest run` — run all tests once (no watch)
- `npx vitest run test/validation.spec.ts` — run a single test file; add `-t "<name>"` to filter by test name
- `npm run lint` — eslint (type-aware, covers `src/` and `test/`)
- `npm run format` — prettier `--write` over the repo; `npm run format:check` to verify without writing. Formatting is not part of `npm run lint`, so it is only enforced by the IDE-on-save setting and by running these.
- `npx tsc --noEmit` — type-check `src/`; `npx tsc --noEmit -p test/tsconfig.json` for `test/` (the root config excludes it)
- `npm run cf-typegen` — regenerate the `Env` type in `worker-configuration.d.ts` via `wrangler types`
- `npm run db:migrate:local` — apply `migrations/` to the local D1. There is deliberately **no** `db:migrate:remote` script: that command rewrites production, D1 has no down-migrations, and it should be typed on purpose (`npx wrangler d1 migrations apply nachbarin --remote`). See README "Operations" for minting and revoking keys.

## Architecture & conventions

- **`src/index.ts` is wiring only** (build `Deps`, delegate). Request handling lives in `src/app.ts`, whose `handleRequest(request, deps)` takes its dependencies as an argument — that injection point is what makes the API testable without a database, so keep logic out of `index.ts`.
- **Module layout**: `app.ts` (routing + error boundary) → `handlers.ts` (the two endpoints) → `validation.ts` (pure, synchronous) / `storage.ts` (the persistence seam). `d1-key-store.ts` and `d1-record-store.ts` are the D1 adapters behind that seam. `http.ts` holds response builders and the capped body reader; `config.ts` holds the limit constants; `auth.ts` holds the `Principal` union.
- **Zero runtime dependencies** — no router, no validation library. Keep it that way unless there's a strong reason.
- **Bindings and runtime config** live in `wrangler.jsonc`; `nodejs_compat` is enabled and `compatibility_date` is pinned there. After changing bindings, run `npm run cf-typegen` so `Env` stays in sync. The one binding is `DB` (D1); `createDeps(env)` reads it.
- **The schema** lives in `migrations/`, applied via `wrangler d1 migrations apply`. Four tables: `installations` (the `(app_id, instance_id)` pair, surrogate `id`), `api_keys` (sha256 hashes, `kind` in `read`/`write`, mandatory `installation_pk`, soft-deleted via `revoked_at`), `records` (`app_data` as JSON text, dates only, `UNIQUE (installation_pk, client_id)`), and `record_submissions` (the operator-only submission log — full timestamps and edge data, swept at 90 days). Read the comments before changing any of them — several constraints are load-bearing and the reasoning is recorded there. **Migrations are append-only history and are never edited after they are applied**, so where two of them disagree the later one wins: `api_keys` was rebuilt by `0002_*.sql`, which is the live account of that table; `0001_*.sql` still describes `installations` but its `api_keys` reasoning is superseded, and `0003`'s "metadata table" is named and described by `0004`. **`0004`'s storage arithmetic is wrong and there is no `0005` to correct it** — it reasons against "D1's 10 GB per-database limit", which is the _paid_ ceiling; the free plan caps a database at 500 MB, so every figure in that section is twenty times too forgiving, and storage is not even the first thing to break (the free plan's 100k rows written/day is, and index writes count against it). The live account is `MAX_SUBMISSIONS_PER_RECORD` in `src/config.ts`, because the cap that answers it needed no schema change and so minted no migration to carry the correction.
- **SQLite does not enforce `VARCHAR(n)` lengths**, so every length limit is a `CHECK` — and it has no date type either, so date formats are `CHECK`ed with `GLOB` too. Two traps live here, both pinned by tests in `test/d1-record-store.spec.ts`:
  - **D1 caps a GLOB pattern at 50 bytes** (stock SQLite allows 50,000), and `[0-9]` costs five of them — ten character classes is the entire budget. Over it, every evaluation fails with `LIKE or GLOB pattern too complex`, **at INSERT and not at migration time**: `migrations apply` will happily accept a CHECK that can never pass. `0003`'s date pattern is at 42 bytes, so the next timestamp format check written here will look reasonable and fail. Use `substr()` plus several short patterns, as `0004` does.
  - **`INTEGER` affinity converts a well-formed integer literal**, so `'3320'` is stored as `3320` and needs no defending. What it will not touch is `'AS3320'` (stays TEXT), a float, or an int64 overflow (becomes REAL) — those compare equal to no integer, silently. `typeof(x) = 'integer'` is the only construct that sees it.
- **`worker-configuration.d.ts` is generated** — do not edit by hand. It is registered in tsconfig `types`, so `Env` is globally available in `src/` without an import. It is in `.prettierignore`, and must stay there: `wrangler types` already formats its own output with `.prettierrc` (it picks up the `prettier` devDependency) but emits the `Env` header with tabs, so letting Prettier reformat those lines makes every `npm run cf-typegen` produce a diff the next save flips back. Ignored, typegen reproduces the committed bytes exactly.
- **Tests** use `@cloudflare/vitest-pool-workers` and run inside the actual Workers runtime (`vitest.config.mts` points at `wrangler.jsonc`). Most specs drive `handleRequest` with the in-memory fakes from `test/fakes.ts` (real dedupe and cursor semantics); `test/worker.spec.ts`, `test/d1-key-store.spec.ts` and `test/d1-record-store.spec.ts` run against a real local D1. `test/` has its own `test/tsconfig.json` and is excluded from the root one. **The pool rolls storage back per test**, so a spec seeds what it needs in the test itself; `beforeAll` seeding (`test/seed.ts`) is copied into every test's frame instead.
- **Migrations in tests**: `vitest.config.mts` reads `migrations/` Node-side (the Workers runtime has no filesystem) and passes them as the `TEST_MIGRATIONS` binding; `test/apply-migrations.ts` applies them per test file via `setupFiles`. `TEST_MIGRATIONS` is declared by hand in `test/env.d.ts` because it is not a real binding and `wrangler types` will never emit it.
- **`FakeKeyStore` stores keys verbatim and should stay that way.** Hashing is an implementation detail of the D1 adapter, not part of the `KeyStore` contract, and no handler test can observe it. The gap that leaves is closed by `test/d1-key-store.spec.ts`, whose golden hashes are **hardcoded, not computed** — deriving them from the code under test would make the assertion a tautology.
- **Style**: 2-space indent, single quotes, semicolons, 140 cols (`.prettierrc`), enforced by `npm run format`. Note `.idea/codeStyles/Project.xml` still says tabs; Prettier wins on save (`.idea/prettier.xml` sets run-on-save). `.prettierignore` covers the two generated files — `worker-configuration.d.ts` and `package-lock.json` — whose generators own their formatting.

## Invariants worth knowing before you change behaviour

These are load-bearing and each has a regression test. Read the comment at the definition before touching them.

- **Never use `Date.parse` on `created_at`.** It does not reject out-of-range days, it silently rolls them over (`2026-02-30` → March 2nd). `validation.ts` range-checks every component, days-in-month included.
- **`rejected` means "never retry".** Clients drop anything acknowledged as `created`/`duplicate`/`rejected` from their queue, so a _transient_ storage failure must throw (→ 500/503) and never be reported as a per-record outcome. `InsertOutcome` has no `rejected` variant for this reason.
- **A write's `results` is positionally aligned with the submitted `records`** — same length, same order. It is not keyed by `client_id`, because a batch may legitimately contain the same one twice.
- **Dedupe is scoped to the installation — the `(app_id, instance_id)` pair — never to `instance_id` alone.** `instance_id` is not globally unique; it defaults to `default`, so two apps at one instance would collide and the second's records would come back `duplicate`, which this protocol defines as success. The client would drop them from its queue and they would be lost silently. The schema gives the pair a surrogate key so `(installation, client_id)` is unambiguous.
- **`app_data` is opaque and never interpreted.** Any JSON value is valid; only presence is required. It is stored as JSON _text_ (D1 is SQLite; there is no `jsonb`) in a `NOT NULL` column — that constraint is what forces a JSON `null` to be stored as the text `null` rather than SQL NULL, which would mean "no payload" and is a fact this protocol cannot express.
- **The `records` table stores dates and never times.** `created_date` is the date of the client's `created_at` in the exhibit's local frame — a `slice(0, 10)`, valid precisely because `created_at` preserves its offset and is never normalized to UTC (`localDateOf` in `validation.ts`). `received_date` is the server's UTC date. Do not add a timestamp column here or return one from `GET`: the exact times belong to `record_submissions`, and `test/records.get.spec.ts` fails if a time reaches the wire. The two dates are in different frames and may differ by one around midnight — a skew smell test, never an exact difference.
- **`records.id` is `AUTOINCREMENT` and `installations.id` deliberately is not.** 0001's "no AUTOINCREMENT" argument is about dangling references, which the FK already prevents, and does not transfer. `records.id` is the public download cursor: without `AUTOINCREMENT`, deleting the highest row lets the next insert reuse its id, and a reader already past that cursor would never see the replacement — no error, both sides believing the transfer finished. This table gets deletions (vandalism cleanup, erasure requests), so it is not hypothetical.
- Identity **and scope** come from the API key alone — never the request body, never the query string. `Principal` also carries `keyId`, which is _which_ key — the log records it, because the hash is one-way and a key's surrogate id is the only handle on it that exists.
- **Every CHECK on `record_submissions` must be implied by something the code already produces** (`validation.ts`, `provenance.ts`, `crypto.randomUUID`). Those rows share the record insert's transaction, so a CHECK that fires is not a rejected log row — it is a rolled-back batch → 500 → client retries → 500, forever. The sharpest case: `RFC3339_RE` accepts a lowercase `t`/`z` and unbounded fractional seconds and `validateCreatedAt` returns the string **verbatim**, so `created_at`'s GLOB uses `[Tt]` and pins no length. Nothing edge-sourced is shape-checked, only bounded, and `provenance.ts` clamps to that bound first. A forensics table must not refuse a row because it looks wrong — looking wrong is the point.
- **The submission log is capped at `MAX_SUBMISSIONS_PER_RECORD` rows per `(installation, client_id)`, and the cap is a `WHERE`, not a CHECK.** It lives in `INSERT_SUBMISSION_SQL` folded into the statement that was already being sent — no extra query, no extra round trip, and the COUNT is self-bounding because the cap limits what there is to scan. A CHECK could not do this (it would roll the batch back, which is the hazard `0004`'s header exists to prevent — and SQLite CHECKs cannot hold subqueries anyway). Two properties are load-bearing and pinned by `test/d1-record-store.spec.ts`: the cap is **invisible to the client** (a capped submission is still reported `duplicate`; `InsertOutcome` has no variant for "not logged"), and it **can only ever withhold a row from a submission that stored nothing**, so "both, or neither" survives. It is flat rather than per-day _because the exhibits reset nightly and lose their queue_, so a client_id cannot be resubmitted across days; if that ever changes, the cap must become per-day.
- **Retention is a cron, and the date-only design depends on it running.** `scheduled` in `index.ts` → `purgeExpiredSubmissions`. Four places rest `records`' datelessness on the timestamps living somewhere with a retention; a sweep that stops makes this a permanent precise-timestamp archive. It must never touch `records` — `test/retention.spec.ts` pins that, and the boundary direction.
- **`KeyStore.resolve` must never turn a database failure into `null`.** `null` means 401, which tells a client its credential is bad — the one conclusion it must not draw from an outage, since a well-behaved client may then stop retrying and discard queued records. Let D1 errors propagate to the 500 boundary in `app.ts`. Neither D1 adapter has a try/catch, and that is the reason.
- **Dedupe is the `UNIQUE (installation_pk, client_id)` constraint, not a preceding SELECT.** `D1RecordStore.insert` uses `ON CONFLICT DO NOTHING` and reads the verdict off `meta.changes` (1 = created, 0 = duplicate) — a read-then-write would let two concurrent retries of one batch both insert. One statement per record per table inside a single `batch()`, never a multi-row `VALUES`: D1 caps a query at **100 bound parameters** — **per statement within a batch**, not per batch — so 2N statements of 8 and 15 params are fine where one of 800 is not. The record statements come first and the log statements are **appended, never interleaved**, so `results[i]` stays the outcome of record `i`.
- **`api_keys.kind` is not derivable from anything, which is why it is a column.** Both kinds carry an installation (`installation_pk` is `NOT NULL`), so `kind` is the only thing separating a key that may download from one that may only deposit. 0001 kept this column for the opposite reason — back then it _was_ derivable, and was stated explicitly so that an operator omitting `installation_pk` got a constraint violation rather than a working global read key. That hazard is now a `NOT NULL` violation; read `migrations/0002_*.sql`, not `0001`, for the current argument.
- **Every key is scoped to one installation, and there is no global read key.** A read key downloads its own installation's records and nothing else, so `GET /v1/records` takes no `app`/`instance` parameter — read scope is authorization, not a filter. Full-corpus export is an operator's SQL query (README "Exporting across installations"), deliberately not an API capability: a token that spanned installations would be a standing credential that reads everything for as long as it exists.
- **The key hash must match `printf %s "$key" | shasum -a 256`** — UTF-8, no trailing newline, lowercase hex. `echo` appends a newline and yields a key that 401s forever, indistinguishably from a revoked one. Pinned by the golden fixtures in `test/seed.ts`.
